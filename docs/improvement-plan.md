## 1. Почему управление «часто уходит к macOS»

Если кратко, приложение задумано так, чтобы при **любом** сомнении сразу отдать управление macOS, и **ничего потом не возвращать само**. В сочетании с особенностями M4 Max это выглядит как постоянные срывы.

### 1.1 Подтверждённая причина: «macOS вернула управление вентилятором 2»

На скриншоте панели (профиль «Прохладный», «Не активен») в подвале именно это сообщение. Его выбрасывает `FanModeController.setTarget` ([FanModeController.swift:127](../Sources/FanMaclyCore/FanModeController.swift)), когда регистр режима вентилятора не равен 1:

- проверка идёт каждые **300 мс** (`tick` → `setTarget` для всех вентиляторов);
- **одно** наблюдение `FnMd ≠ 1` → `restore()` → новый `automaticFallbackID` → приложение сбрасывает выбранный режим в «Автоматически»;
- сообщение возникает и при **неудачном чтении** регистра (`mode(fan:)` вернул `nil`), то есть одна сбойная транзакция SMC неотличима от реального перехвата.

Почему регистр может откатываться:

1. **`Ftst` не захватывается на M4 Max.** На этом Mac режим автоматики — `FnMd = 0` (а не 3). Код выставляет `Ftst = 1` только для режима 3 или после отказа записи `0x82`. Если прямая запись `FnMd = 1` принята, `Ftst` остаётся 0 — и `thermalmonitord` вправе забрать вентилятор обратно.
2. **В системе работает чужой root-помощник `com.crystalidea.macsfancontrol.smcwrite`** (Macs Fan Control, PID 831). Два писателя SMC — классический источник «необъяснимых» откатов режима и сбойных чтений.

### 1.2 Пороги «максимального охлаждения» не подходят для M4 Max

Срез SMC под обычной нагрузкой (macOS сама держала ~4 000 об/мин):

| Показатель | Значение | Порог FanMacly |
|---|---|---|
| Управляющее CPU (`TCMb`) | 81–85 °C | ≥ 85 °C → сразу максимум |
| Максимум 134 «CPU»-каналов | 95–109 °C | ≥ 100 °C → сразу максимум; ≥ 90 °C 2 с → максимум |
| Условие выхода | — | управляющее < 80 °C **и** пик < 90 °C 5 с подряд |

На Apple Silicon пики 100–110 °C на отдельных каналах — обычная работа. Следствия:

- любой профиль под нагрузкой превращается в **5 777 об/мин** («Активен · Макс.») и почти никогда из этого не выходит;
- кривая обязана достигать 100 % не позже **85 °C** (`CoolingCurve.isValid`), а 85 °C для M4 Max — это рабочая температура. Профили «Прохладный»/«Сбалансированный» под нагрузкой всегда на максимуме;
- «пик» считается по 134 каналам, которые попали в группу CPU эвристикой по префиксу (`Tp`, `Te`, `TP`, `TE`…). Часть из них, вероятно, не температуры ядер — это добавляет выбросов.

### 1.3 Ничего не возобновляется автоматически

| Событие | Что происходит | Что видит пользователь |
|---|---|---|
| Сон / закрытие крышки | `helper.disconnect()`, `selectedMode = .system` | после пробуждения — снова «Автоматически» |
| Перезапуск приложения / вход в систему | выбранный режим не сохраняется | всегда стартует в «Автоматически» |
| Любой защитный возврат | новый `automaticFallbackID`; старые запросы отклоняются | режим нужно включать руками заново |
| Перезапуск помощника | журнал снимает ручной режим | то же |

Это сделано сознательно ради безопасности, но для пользователя неотличимо от «программа постоянно отваливается».

### 1.4 Хрупкая аренда управления (heartbeat)

- Приложение шлёт heartbeat раз в 2 с из `Task` на главном акторе; помощник отпускает управление через 8 с тишины, приложение само рвёт связь через 6 с без ответа, `apply` ждёт ответа 6 с.
- У приложения `LSUIElement`, и нигде нет `ProcessInfo.beginActivity` — при закрытой панели оно кандидат на **App Nap**, который может растягивать таймеры. Не проверено измерением, но риск реальный.
- Безопасность при этом уже обеспечивает помощник (root, свои проверки датчиков раз в секунду). Жизнь UI-процесса для безопасности почти не важна, а срывы из-за неё — вполне.

### 1.5 Мгновенный возврат при любом сбое данных

`validate()` бросает исключение при **одном** снимке, где у вентилятора не прочиталось `Ac/Mn/Mx`, `FNum`, нет CPU-датчиков и т. п. Допуска на транзиентные ошибки (2–3 с подряд) нет. С конкурентом за SMC это особенно заметно.

### 1.6 Диагностика не позволяет узнать причину

Помощник пишет `NSLog("%@")` — в системном журнале всё превращается в `<private>`. За 3 дня в журнале 20 строк без содержания. Причину срыва нельзя восстановить постфактум, и в README это несколько раз признаётся («исходный эпизод не реконструируется»).

## 2. Анализ UI/UX

Скриншот: вкладка «Профиль», 350 pt шириной, ~600 pt высотой.

### Что хорошо
- Нативный AppKit, Liquid Glass на macOS 26+, тёмная/светлая тема, доступность, моноширинные цифры.
- Быстрый обзор трёх температур в шапке.
- Виджет Пункта управления (Авто / Профиль / Макс.).

### Проблемы

**Модель режимов непонятна**
1. Режим выбирается маленьким всплывающим меню на вкладке «Вентиляторы», а профиль редактируется на вкладке «Профиль». На скриншоте профиль «Не активен», но **кнопки «Включить» нет** — включается он неявно, если подвинуть ползунок.
2. «Автоматически / Вручную / По температуре» — технические режимы, а не намерения пользователя («тихо», «помощнее», «максимум»).
3. Профили «Прохладный»/«Сбалансированный» спрятаны в выпадающем меню второго уровня.

**Статус и ошибки**
4. Ошибка — серая строка мелким шрифтом в подвале, без действия «Вернуть режим» / «Почему?». Сообщение `status.message` нельзя скрыть (кнопка «Скрыть» показывается только для `helper.error`).
5. Когда панель закрыта, о возврате к macOS не узнать: нет уведомления, значок в строке меню не меняется.
6. Строка «CPU 88°» без контекста: нормально это или плохо? Нет цветовой шкалы относительно чипа.

**Редактор кривой**
7. Температурные точки зафиксированы (40/55/65/75/85 °C), двигать можно только проценты. Ось заканчивается на 85 °C — текущие 88 °C вне графика, рабочая точка не видна.
8. Проценты вместо оборотов; «Расчёт, %» — жаргон. Неясно, как 45 % звучит и сколько это об/мин.
9. Пять ползунков дублируют график — по точкам графика нельзя тянуть.
10. Ползунки неактивны без помощника, хотя редактировать профиль можно и без него.

**Структура и визуал**
11. Три «стеклянные» кнопки-вкладки тяжелее и занимают больше места, чем сегментированный контрол; высота панели прыгает между вкладками (~290 → ~600 pt).
12. «Датчики» — сотни ключей SMC, большинство с неизвестным назначением; группировка эвристикой ошибается (например, `Tsx1` → «Корпус», `Tf46` = 101,9 °C в «Других»).
13. Подсказки перегружены внутренней кухней (iSMC, TCMb, медиана 3 отсчётов) — это уместно в «Диагностике», не в основном интерфейсе.
14. Настройки, диагностика, управление помощником и «Завершить» — в одном меню-шестерёнке; отдельного окна настроек нет.
15. Терминология плавает: «помощник», «автоматика», «Управляет macOS», «Мониторинг», «Защита».

## 3. Потребности пользователей

| Кто | Задача («когда…, хочу…, чтобы…») | Что нужно от приложения |
|---|---|---|
| **Тишина** — работа, созвоны, ночь | когда нагрузка небольшая, хочу тишины и не думать о вентиляторах | тихий профиль, остановка вентиляторов на холостом ходу, стабильность после сна |
| **Производительность** — сборки, рендер, игры, LLM | когда запускаю тяжёлую задачу, хочу заранее раскрутить вентиляторы, чтобы чип не троттлил | одна кнопка «Буст» (на N минут), автопрофиль по приложению, высокий потолок до вмешательства |
| **Наблюдение** | хочу одним взглядом понять, всё ли в порядке | температура и обороты в строке меню, цветовой статус, история за 10–60 мин |
| **Все** | хочу доверять: если что-то пошло не так, понять что и вернуть свой режим одним нажатием | понятный баннер с причиной, уведомление, журнал событий, автовозобновление |

Главные выводы:
- **Настроил и забыл.** Режим должен переживать сон, перезапуск и транзиентные сбои. Сейчас это главный провал.
- **Намерения важнее механики.** Пользователь выбирает «Тихо / Баланс / Мощно / Макс.», а не «по температуре + кривая».
- **Прозрачность без жаргона.** Причина смены режима — простым языком, детали — по запросу.

## 5. План улучшений

### Фаза 0 — подготовка (0,5–1 день)
- [ ] `git init`, первый коммит; убрать zip-резервные копии исходников из `build/` в историю git.
- [ ] Перевести логи помощника и приложения на `os.Logger` с публичными полями: режим, `FnMd`, `Ftst`, `FnTg`, `FnAc`, причина возврата.
- [ ] Журнал событий управления (кольцевой буфер ~200 записей в помощнике; отдаётся через XPC) — основа для экрана «Почему режим изменился».
- [ ] Скрипт длительного теста: 30–60 мин нагрузки + `fanmacly-probe --fan-audit` + подсчёт возвратов.

### Фаза 1 — надёжность управления (главная боль, 3–5 дней)
1. **Захват `Ftst`.** При наличии ключа выставлять `Ftst = 1` до записи `FnMd = 1` на всех моделях, включая режим 0. Проверить на M4 Max длительным тестом.
2. **Повторный захват вместо возврата.** Откат `FnMd` или неудачное чтение → переход в состояние «перехватываем» и повторный захват (например, до 5 попыток за 10 с). Возврат к macOS только после исчерпания попыток.
3. **Допуск на транзиентные ошибки.** Для класса «данные недоступны» — возврат только после 3 с подряд плохих снимков. Немедленный возврат оставить для действительно опасных случаев.
4. **Сохранять намерение пользователя.** Помощник хранит выбранный режим и параметры (`/var/db/app.fanmacly/intent.json`) и сам возобновляет их после пробуждения, перезапуска приложения и своего перезапуска. Приложение перестаёт сбрасывать `selectedMode` при сне.
5. **Помощник — сторож.** Убрать жизнь UI как условие аренды: помощник продолжает профиль без приложения. Оставить короткую аренду только для опасного состояния «ручной 0 об/мин». Если аренда остаётся — `beginActivity` и тайм-аут ≥ 30 с.
6. **Пороги под Apple Silicon.**
   - Решения принимать по управляющему датчику (`TCMb`), а не по максимуму 134 каналов. Пиковые каналы — только с устойчивостью (например, ≥ 105 °C в течение 5 с).
   - Буст до максимума: управляющее ≥ 95 °C. Выход — с гистерезисом 5–7 °C.
   - `thermalState == .serious` → форсировать максимум и **сохранить** управление; `.critical` → отдать macOS.
   - Ось кривой 40–100 °C, последняя точка до 100 °C (а не жёстко 85). Пороги — в таблицу по семействам чипов.
7. **Автовозобновление после защиты.** После защитного возврата и подтверждённого остывания (например, 60 с) — вернуть выбранный режим (настройка, по умолчанию включено) с уведомлением.
8. **Обнаружение конфликтов.** Найти известные помощники (Macs Fan Control `smcwrite`, TG Pro и т. п.) и показать предупреждение: «Другое приложение управляет вентиляторами».
9. **Тесты:** откат `FnMd` → повторный захват; транзиентные чтения; сон/пробуждение → возобновление; serious → максимум без возврата.

**Критерий готовности:** за 60 минут смешанной нагрузки, включая сон, — 0 незащитных возвратов к macOS; время в выбранном режиме ≥ 99 %.

## 6. Порядок и оценка

| # | Блок | Эффект для пользователя | Оценка |
|---|---|---|---|
| 0 | git, логи, журнал событий | видно, почему срывается | 0,5–1 д |
| 1.1–1.3 | `Ftst`, повторный захват, допуск ошибок | убирает основную массу срывов | 1–2 д |
| 1.4–1.5, 1.7 | намерение в помощнике, автовозобновление | «настроил и забыл» | 2–3 д |
| 1.6 | пороги под M4 Max | профили перестают выть на максимуме | 0,5–1 д |

Рекомендуемый старт: **Фаза 0 → 1.1–1.3 → длительный тест на этом Mac**. Это быстро покажет, сколько срывов вызывал `Ftst`/конкурент, а сколько — пороги и сон.

## 7. Что проверить вручную до начала
- Закрыть или удалить Macs Fan Control вместе с его помощником (`/Library/PrivilegedHelperTools/com.crystalidea.macsfancontrol.smcwrite`) и посмотреть, станет ли меньше срывов. Это самый дешёвый эксперимент.
- Посмотреть, на каких событиях срывы случаются чаще: сон, нагрузка, закрытая панель.
